# 两类主导物理失败模式的专用检测器：变点臂 × 持续臂 × 阈值臂

`moe-failure-mode-detectors-0906`，2026-09-06。
全部产物只写在本目录；未修改任何既有目录，未执行任何 git 命令；全程 CPU。

被检验的假设：`object_released_or_dropped_before_goal`（下称 **掉落**）是一个**变点**——抓稳过又丢了，
应当有"抓握期路由 → 断裂"的转折；`stable_grasp_not_observed`（下称 **未抓稳**）是一个**持续异常**——
从头就不对、反复重试，因此"用本集自身最初几个 chunk 做基线"的做法在它身上应当**失效**。
预测的形状是一个交互：变点臂在掉落上优于阈值臂，持续臂在未抓稳上优于阈值臂。

> **标签性质**：两类模式在 `VLA_MUI_HUB/physical-failure-labels` 中的
> `failure_reason_confidence` 均为 `medium`（全表 1,377 条 medium / 65 条 high）。
> 它们是对回放中**物理结果**的标注，不是对内部机制的证据。
> 本报告凡是以模式为条件的结论，都只在"这批标注正确刻画了物理结果"这一前提下成立；
> 任何"路由里存在抓握断裂表征"的说法都**没有**被本工作证明。

## 1. 交互不存在

### 1.1 2×3 表（公平口径：external 上**匹配虚警**的臂上界）

单个"在 dev 选、冻结后搬到 ext"的工作点无法跨臂比较，因为两队列组成不同
（dev 有 2,800 条 libero_long，ext 有 4,000 条），同一报警率给出的 lead≥4 虚警数可差 6 倍
（例：`selected_mass|L2` 阈值臂 dev 22 FP → ext 127 FP）。
所以主表用**在被评队列上把虚警固定住**的臂上界：

> ceiling(f) = 该臂所有工作点中，在 lead≥4 且 FP≤f 时该模式 TP 的最大值。

这是**上界**（工作点用被评队列的结果挑），不是部署数字；只有与 null 池、与无 cap 基线一起看才有意义。

**external_8b，lead ≥ 4，FP ≤ 57，headline 通道池**（`results/arm_frontier.csv`）：

| 模式 | 阈值臂（对照） | 变点臂 | 持续臂 | 地板 |
|---|---|---|---|---|
| **掉落**（n=241） | **107/241**（54 FP）<br>`hb_entropy_action\|L2` | **122/241**（44 FP）<br>`state_mobility_d0\|L12` | **117/241**（51 FP）<br>`flow_path\|L3` `persist_run` | 50/241 |
| **未抓稳**（n=143） | **62/143**（27 FP）<br>`mobility_d0\|L5` | **66/143**（43 FP）<br>`token_differentiation_d0\|L2` | **73/143**（47 FP）<br>`mobility_d0\|L14` `persist_cycles` | **112/143** |

地板 = max(无 cap 固定 chunk 基线, 各 null 池上界)。掉落一行三个臂都远高于地板；
**未抓稳一行三个臂都低于地板 39–50 个 TP**。

**交互（差中差，按任务聚类的 bootstrap，2,000 抽样，每次抽样内重新取最大值）**：

| 对比 | 掉落上的增益 | 未抓稳上的增益 | 差中差 | p（符号） |
|---|---|---|---|---|
| 变点臂 − 阈值臂 | **+15** [−20, +39] | **+4** [−10, +14] | **+11** [−25, +39] | 0.544 |
| 持续臂 − 阈值臂 | **+10** [−26, +30] | **+11** [−2, +53] | **−1** [−64, +22] | 0.699 |

**结论：交互不存在。** 两个差中差的置信区间都跨过 0，符号检验 p = 0.54 / 0.70。
点估计里只有"变点臂在掉落上比在未抓稳上多赚 11 个 TP"勉强朝假设的方向，
但持续臂在两个模式上的增益几乎相同（+10 vs +11），完全没有"持续臂专治未抓稳"的迹象。

## 3. 分模式打靶是否胜过一个不分模式的检测器？——不稳定，两次赢两次输

做法：同一个臂里，用 dev 预算 B 选一个"打全部风险"的检测器；
再用 B/2 各选一个掉落头和一个未抓稳头，取**最早报警**并起来
（部署时监控不知道会遇到哪种模式，必须同时跑两个头）。
对照组是"同样两个头，但两个都打全部风险，且强制换通道"——如果分模式并不比它好，增益就来自集成而非分模式。
读数取每个族里 external 虚警最接近 57（`v7_guard` 的锚点）的工作点：

| 臂 | 单检测器 | 两个模式头并集 | 两个不分模式头并集（对照） |
|---|---|---|---|
| 阈值 | 199/564 @49 FP（85 掉落 / 58 未抓稳） | **323/564 @56 FP（170 / 77）** | 187/564 @57 FP（104 / 31） |
| 变点 | 192/564 @43 FP（61 / 66） | 284/564 @69 FP（122 / 76） | **330/564 @60 FP（146 / 90）** |
| 持续 | 214/564 @63 FP（112 / 30） | **315/564 @53 FP（134 / 85）** | 245/564 @68 FP（125 / 39） |
| 任意 | 192/564 @43 FP（61 / 66） | 237/564 @60 FP（91 / 83） | **363/564 @70 FP（163 / 95）** |
| 参照 | `v7_guard` 347/564 @57 FP（134 / 98） | | |

**两个头总是明显强过一个头**（例如阈值臂 323 对 199），但**"两个头分别打两个模式"并不稳定地强过
"两个头都打全部风险"**：4 个臂里 2 个赢、2 个输，幅度都在 60–130 个 TP 量级。
结论：**收益来自"跑两个不同通道的头"，不是来自"按模式分工"。**
并且没有任何组合在 ~57 FP 处超过 `v7_guard` 的 347/564。

## 4. 必要的对照：地板不是只有那条基线

无 cap 固定 chunk 基线（"跑到第 q0 步还在跑就报警"，q0 ∈ [2,40)）在 external 上按模式拆开：

| q0 | FP(lead≥4) | 全部 | 掉落 | 未抓稳 |
|---|---|---|---|---|
| 24 | 499 | 424/564 | 150/241 | 117/143 |
| 37 | 60 | 274/564 | 50/241 | **112/143** |
| 39 | 28 | 274/564 | 50/241 | **112/143** |

**未抓稳模式的 78.3%（112/143）可以被一条不看任何路由的"还在跑"规则以 28 个虚警抓到**，
因为 112/143 落在 libero_long（cap 52）。本工作三个臂在 ≤57 FP 下的上界是 62 / 66 / 73，全部低于 112。

两条必须写下来的机制性发现：

1. **`q0 ≥ cap − 4` 时基线等于标签本身。** libero_long cap = 52，q0 = 48 时
   "还在跑且 lead≥4" ⟺ length ≥ 52 ⟺ risk，于是 274 TP / **0 FP**，与 suite 内 risk 标签逐条相同
   （`results/baseline_leak_diagnostic.csv` 已断言）。这就是协议把扫描停在 q0 = 39 的原因；
   本报告的"超出基线"一律只用协议内的 q0 < 40。
2. **在 ≤27 个虚警以下，协议基线在 external 上没有可用工作点**（最省的 q0=39 就要 28 FP）。
   所以任何 FP < 28 处的"超出基线"实际上只是在跟"永不报警"比。读第 1、2 节的小 FP 数字时必须记住这一点。

### null 池：同样的统计量，无内容的通道

| null 通道 | 臂 | external，FP≤57 | 掉落 | 未抓稳 |
|---|---|---|---|---|
| `ctrl_white_noise` | 阈值 | 5/564 @53 FP | 5/241 | 5/143 |
| `ctrl_white_noise` | 变点 | 18/564 @40 FP | 7/241 | 7/143 |
| `ctrl_white_noise` | 持续 | 91/564 @38 FP | 22/241 | 42/143 |
| `ctrl_const_elapsed`（chunk 计数器） | 持续 | **274/564 @14 FP** | **50/241** | **112/143** |
| `ctrl_episode_const_rand`（每集抽一次的常数） | 变点 | **255/564 @20 FP** | 48/241 | **104/143** |

- **chunk 计数器 + run-length = 无 cap 固定 chunk 基线，一分不差。**
  一个零内容通道拿到了 274/564（含 112/143 未抓稳）。任何"持续/游程"统计量在慢变通道上都会退化成时长规则。
- **每集常数 + 变点统计量拿到 255/564 @20 FP。** 直接验证过它就是时长规则：
  只在 libero_long 触发，触发集最短长度 38，中位报警 chunk 42，
  P(触发 | length ≥ 50) = 0.913，P(触发 | length < 50) = 0.0012。
  原因是"逐 chunk 总体标准化"给常数通道注入了确定性时间趋势，而 CUSUM 的 √(n₁n₂/(n₁+n₂)) 尺度随 chunk 增长。
  **本工作实现的变点臂本身就部分是一个时长统计量**——这是我自己设计里的缺陷，靠这个对照抓出来的。
- **LOTO 下白噪声的持续臂拿到 28/143 未抓稳**，高于 headline 池任何未抓稳头的 LOTO 成绩（3–17/143）。
  也就是说：**留出任务后，真实路由通道在未抓稳模式上打不过白噪声。**

### 其余强制对照

- **同发射率零对照**：白噪声/每集常数通道上，在无 cap 基线同虚警下的**超出量**最大为
  **0**（development，89 个工作点）/ **+1**（external，93 个）。任务书说"零对照在每个虚警预算下都拿到 0/564 真阳性"，
  在本框架里这句话只可能指**超出基线的 TP**：一个发几百次警的零检测器，其**原始** TP 必然不为零
  （本框架实测最高 318/487 dev、382/564 ext）。两个量都列出，避免把 0/564 读成原始计数。
  作为交叉检查，把 `capfree_protocol.rate_matched_null` 施加到 311 个**已发布**报警向量上，
  超出量最高可达 +21（dev）/ +27（ext），因此"恒为 0"只在控制通道自身构成的零臂上成立。
- **length 是负对照，不是基线**：`length ≥ cap` 按构造召回 487/487 与 564/564（recall = 1.000），且需要 cap；
  标为 `is_baseline = False`，不进任何排名（`tests/test_protocol.py::test_length_is_a_negative_control_not_a_baseline`）。
- **并列一律 `>=`**：在本工作自己的工作点上，改成严格 `>` 会丢掉
  `set_dwell` 78.5%（dev）/ 77.2%（ext）的报警、`query_top1_churn` 28.8% / 57.8%、`query_hard_churn` 0.5% / 0.9%。
  并列组确实会触发（`results/check_tie_group.csv`）。
- **单集内信息量**：`set_dwell` 在各层的集内常数比例 46.2%–88.5%（均值 72.4%），
  其余 28 个路由量全部为 0.000；三个每集常数对照为 1.000（bit-constant，48 个通道）。
  headline 池的规则（事先固定）是"集内常数比例 ≤ 25%"，因此 `set_dwell` 全部 8 层被排除出主结论，
  只在 `flagged` 池里出现——而它在那里做的事恰好是上面那条时长规则：
  `set_dwell|L2` + `persist_run` 给出 112/143 未抓稳 @14 FP，与 chunk 计数器给的**完全同一个数**。
- **`expert_load_effective_rank` 全程禁用**（= exp(A+B)/32，A、B 反向抵消）；
  `token_entropy` 与 `token_differentiation` 在第 0 步与第 9 步分别提供，从不相加。
- **检测器输入只有 chunk 序号 + 路由**：无 cap、无 phase、无任务身份、无 `per_task` 门限
  （`tests/test_engine.py::test_no_detector_input_uses_the_cap`）。

## 5. 无法区分的东西

1. **"未抓稳的方法" vs "KITCHEN_SCENE8 的方法"**：无法区分，且证据倾向后者。
   87/143 external 未抓稳案例在这一个任务里；留出它以后三个臂在它上面拿到 2/87、0/87、0/87；
   pooled 选出的头在第二大的未抓稳任务上拿到 0/24、0/24、0/24。
2. **"检测未抓稳" vs "检测长时程"**：无法区分。不看任何路由的"还在跑到 q0=39"以 28 FP 拿到 112/143，
   高于本工作三个臂的上界（62 / 66 / 73 @≤57 FP）。
3. **"变点统计量" vs "时长统计量"**：在慢变通道上无法区分。每集常数通道的变点臂拿到 255/564 @20 FP，
   经验证是纯粹的时长规则。因此第 1 节里变点臂在掉落上的 +15 不能被解读为"检测到了抓握断裂"。
4. **机制 vs 标注**：两类模式都是 `medium` 置信度的物理结果标注。本工作没有、也不可能从中推出
   "路由中存在抓握状态的表征"。任何这类说法都超出证据。
5. **小虚警区的"超出基线"**：在 external FP < 28 处协议基线没有可用工作点，
   那里的"超出"只是与"永不报警"相比，不能当作战胜了基线。
6. **持续臂 vs 变点臂在未抓稳上的差别**：上界 73 vs 66，bootstrap 区间
   [18, 205] 与 [17, 168] 大幅重叠（区间宽是因为按任务重采样时 KITCHEN_SCENE8 被抽到的次数主导了结果）。
   无法判定哪一个更好。
7. **虚警数不跨队列迁移**：同一报警率在 dev 与 ext 给出的 lead≥4 虚警数可差 6 倍（22 → 127），
   根源是两队列的 suite 组成不同（long 2,800 vs 4,000）。
   因此"冻结数值门限"与"匹配报警率"两套数字都列了，两者不可混用。
8. **external 不是一次性密封评测**：见下。

## 6. 协议与诚实性

- **拟合在 `development_main`，评测在 `external_8b`**。选择只用 development 的结果；
  逐 chunk 参考分布（中位数 / IQR）、持续臂的门（development 的 0.90 与 0.975 分位）、
  以及门限网格序号 k 全部在 development 上冻结。
- **external 的两种搬运方式都报**：`frozenvalue`（直接用 development 的数值门限）与
  `ratematched`（同一 k，用 external **无标签**的路由分布重算门限）。主表用后者，前者在
  `results/selected_operating_points.csv` 的 `extF_*` 列。两张表逐行对齐（已断言）。
- **开发迭代次数：4 次，且我在最终设计定下来之前就看过 external。** 明确写下来：
  四轮 development→external 都算了 external 数字。四轮之间改动的只是标定与报告机制，
  臂、统计量、提前量预算、度量在第一轮之前就固定且从未改动：
  (1) 门限网格原本按 development 非风险回合参数化，因为无法在无标签队列上重建而替换；
  (2) 换成无标签的报警计数网格；
  (3) 发现 lead≥4 虚警数不跨队列迁移后，加了 rate-matched 第二张 external 表；
  (4) 发现 chunk 计数器能一分不差地重现固定 chunk 基线后，把对照池拆成白噪声 / chunk 计数器 / 每集常数，
  并把"地板"重新定义为基线与对照池上界的最大值。
  因此本报告的 external 数字不是一次密封评测。缓解的事实是：本报告的主结论全部是否定性的
  或由对照驱动的，而这种泄漏只会朝相反方向起作用。
- **LOTO 的一个残余泄漏**：逐 chunk 总体参考分布与持续臂的门是在**全部** development 任务上池化的，
  没有在每个 fold 内重算。它不使用任何结果标签（只是 chunk q 上路由值的中位数与 IQR），
  因此不会泄漏结果信息，只可能泄漏任务构成信息；每个 fold 只移除 400/14,800 条回合。
- 随机种子 20260906；bootstrap 单位是任务（external 39 个）。
- 复用而非重写：度量、基线扫描、同发射率零对照来自 `moe-capfree-0906/experiments/capfree_protocol.py`；
  队列装配、路由块与同任务定 chunk AUC 估计量来自 `moe-early-window-0906/experiments/common.py`。
  两者都是 import，没有复制实现。
- 未读取、未写入、未依赖 `moe-cusum-capfree-0906/`。

## 7. 一句话结论

**假设被否定。** 没有 mode × arm 交互：
变点臂对掉落的增益 +15/241 [−20, +39]、持续臂对未抓稳的增益 +11/143 [−2, +53]，
两个差中差分别是 +11 [−25, +39]（p=0.54）和 −1 [−64, +22]（p=0.70），
在诚实部署口径下符号还会反转。
掉落模式确实有可跨任务迁移的路由信号（LOTO 121/241 @53 FP，pooled 上界 122/241 @44 FP），
但它对统计量的形状**不敏感**——三个臂在 44–54 FP 处给出 107 / 122 / 117，差别落在噪声里。
未抓稳模式则连"是一个模式"都无法与"是一个任务"和"是一个长时程"区分开：
它的 pooled 成绩在留出承载任务后从 39–73/143 掉到 3–17/143，
而一条不看路由的"还在跑"规则以更低的虚警拿到 112/143。
