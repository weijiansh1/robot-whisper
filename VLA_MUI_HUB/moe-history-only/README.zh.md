# 只使用历史 MoE，能否尽早判断 rollout 做错了？

## 结论

找到了一个可复现的候选模式：**相对于自身初期，跨重规划的 HB 路由变化幅度持续下降**。
但本次实验**没有找到足以跨任务通用、并且能在多数物理错误发生前报警的关键点规则**。
目前它更适合描述后续停滞风险。不能把它解释为已经证明“我做错了”，也不能把没有报警解释为正确。

这里的负结果限定于本次检验的三类模式、初轮 20 个固定规则和后续 3 个确认次数变体，不是对全部 MoE 信息的不可预测性证明。
尤其不能把有限规则扫描的最好成绩当作信息论上限。

## 数据和约束

从原始 `server/routes.zarr` 重新提取特征，而不是采用旧报告的性能数字。
主评估覆盖全部 40 个 LIBERO 任务、34,560 条自然轨迹：33,157 成功、1,403 失败。

| 采集批次 | 轨迹 | 失败 |
|---|---:|---:|
| right-16x32 | 2,560 | 307 |
| right-50x8-20260903 | 16,000 | 532 |
| right-50x8b-20260903 | 16,000 | 564 |

`pin-base` 是重复对照，`pin-on/off` 是干预，均单独计分。
还核验了两批 CALVIN 的 1,178 个已执行子任务、107 次失败。其任务链只采集了 80/1000、200/1000，
且两批可能有重复初态或任务链，因此不与 LIBERO 合并，也不作为独立重复样本。
CALVIN 的 `episode_id` 全零；依据 evaluator 每个子任务重新创建动作队列的行为，
用 `ceil(environment_steps / replan_steps)` 重建边界，并逐链核对 `inference_calls`，核对全 store 总行数。

总计读取 91 个来源、37,276 条 LIBERO 轨迹或 CALVIN 子任务。
所有 LIBERO 的 episode 顺序、长度和全局 control_step 连续性均已核验。

检测器采用比“只用历史 MoE”更严格的解释：**只用本条轨迹当前及之前的路由概率**。
不读其他轨迹，不用成功参考集，不拟合阈值或权重，不训练模型，不使用任务身份、初态、动作、图像、
物理状态、最终长度或时间上限。标签和物理事件只进入事后评估。

当前 query 的 MoE 在推理完成后已经可用，报警发生在执行该 query 动作之前。
若要求只能使用上一次推理的数据，`previous_query_only_metrics.csv` 另给出延迟一 query 的结果。

这些队列已被仓库中的其他实验探索过。本结果属于重新核验后的回顾性研究，不能称为全新盲测。

## 一个可直接实现的模式

取最后一个 denoising step 的十个 action token、每层完整的 32 路 softmax 概率。
对每个 HB 层，计算相邻两次重规划中同位置 action token 的平均 Hellinger 距离：

```text
m[q, layer] = mean_action H(p[q, layer, action], p[q-1, layer, action])
base[layer] = mean(m[1:5, layer])
r[q] = median_layer(m[q, layer] / base[layer])
s[q] = max(mean(r[q-2:q]), mean(r[q-1:q+1]))
alarm[q] = (s[q] <= threshold), q >= 7
```

上述切片为 Python 的左闭右开约定；`r` 在 q5 才开始用于检测，基准固定为 q1..q4。
这相当于两 query 平滑、连续两次确认。分层先取比值，再聚合，避免直接混用各层不同尺度。
零基准时不作判断。使用平方根概率的距离形式，避免 `1 - affinity` 在小距离处的数值抵消。

预先声明的主规则是 L12..15、阈值 1/4；阈值 1/2 和全部八层等是预先列出的敏感性规则。
主规则没有因为结果不理想而被替换；下面同时报告有信息的敏感性结果，不能把它们包装成事先选定的最佳方法。

## 检出率、误报与时间

| 固定规则 | 检出失败 | 成功误报 | 失败召回 | 成功误报率 | 报警后最终失败比例 | 半程前检出 / 全部失败 |
|---|---:|---:|---:|---:|---:|---:|
| 后层降至 1/4，预设主规则 | 25 | 0 | 1.78% | 0% | 100% | 0 / 1403 |
| 后层降至 1/2 | 940 | 783 | 67.00% | 2.36% | 54.56% | 100 / 1403 = 7.13% |
| 全部层降至 1/2 | 420 | 145 | 29.94% | 0.44% | 74.34% | 56 / 1403 = 3.99% |

**后续探索发现，持续确认很关键。** 初轮的部分成功误报只是短暂下降后恢复。
保持后层、阈值 1/2、初期基准和两 query 平滑不变，额外检查 1/4/8 次确认：

| 连续确认次数 K | 检出失败 | 成功误报 | 召回 | 误报率 | 报警后最终失败比例 | 半程前检出 |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 1,030 | 2,673 | 73.41% | 8.06% | 27.82% | 140 / 1403 |
| 2，初轮规则 | 940 | 783 | 67.00% | 2.36% | 54.56% | 100 / 1403 |
| 4 | **726** | **56** | **51.75%** | **0.169%** | **92.84%** | **50 / 1403 = 3.56%** |
| 8 | 455 | 19 | 32.43% | 0.057% | 95.99% | 30 / 1403 |

K=4 是本次较高置信度的候选：首次失败报警中位数 q32、全程比例中位数 69.2%，
到记录终点的后续推理数中位数 15；最早可在 q9、第十次推理完成后、执行该 chunk 动作前确认。
它把短暂下降过滤掉了，但没有解决多数失败的早期识别，半程前只有 50 条。
K=8 的中位报警进一步推迟到 q37。
这三条是看到初轮结果后增加的探索性规则，不能声称是预注册或独立验证；没有训练模型、拟合阈值或学习权重。

“尽可能早”需要同时给出误报代价。本次输出的是每个固定规则的首次合法确认时刻，
不是看完一条失败轨迹后回选的最早异常，也没有声称这些规则达到所有可能方法的最优前沿。
严格滞后一 query、完全不读取本次推理时，K=4 检出 677 条失败、误报 52 条成功，precision 92.87%。

半程的定义是 `(alarm_query + 1) / recorded_inference_calls <= 0.5`，只用于回顾性评价。
时间上限、完整轨迹长度均不进入检测器。未检出的失败仍保留在召回分母中。
25 次报警零误报是本样本的观察，不是对新轨迹的零误报保证。

后层 1/2 规则的首次失败报警中位数为 q29；相对全程的中位数为 67.3%，
到记录终点还剩 16 次后续推理的中位数。全层 1/2 为 q20、81.8%、5 次后续推理。
绝对 query 的中位数和相对比例的中位数来自不同任务时长，不能相互直接换算。

初轮两次确认规则最早可以在 **q7，即第八次推理、约执行过 70 个策略动作后**报警。
但后层 1/2 规则在 q10 及以前仅捕获 28/1,403 次失败；截至 q15 为 103/1,403。
全程前 65% 捕获 374/1,403 = 26.66%。这说明“有个别很早的案例”和“多数失败都能很早判断”差别很大。
这里的动作数不含环境 settle 步数，也不是秒数。

按任务进行 2,000 次簇 bootstrap，后层 1/2 的召回区间约 53.9%--72.8%，
误报率 0.93%--4.10%，precision 27.1%--77.6%。按任务初态、按批次 seed 的区间另列在
`cluster_intervals.csv`。任务间差异不能用把 34,560 集当作独立样本的窄区间来掩盖。

## 为什么还不能称为统一的“我错了”信号

**跨任务差异很大。** 后层 1/2 的结果如下：

| suite | 失败数 | 检出失败 | 成功误报 | 报警后最终失败比例 |
|---|---:|---:|---:|---:|
| goal | 250 | 158 | 1 | 99.4% |
| long | 757 | 550 | 112 | 83.1% |
| object | 81 | 35 | 664 | 5.0% |
| spatial | 315 | 197 | 6 | 97.0% |

同样的下降模式在 object 上主要出现于最终成功的轨迹。
在两批较大的采集中，后层 1/2 的 precision 分别为 47.6%、46.6%；合并旧的 16x32 后才是 54.6%。
因此不能把合并后的概率直接当作新任务的失败概率。
K=4 过滤短暂下降后，在四个 LIBERO suite 中的 precision 都提高了，但短任务报警依然晚：

| suite | K=4 检出失败 | K=4 成功误报 | precision | 中位报警相对全程比例 |
|---|---:|---:|---:|---:|
| goal | 94 | 0 | 100% | 85.0% |
| long | 476 | 51 | 90.3% | 67.3% |
| object | 26 | 1 | 96.3% | 82.1% |
| spatial | 130 | 4 | 97.0% | 95.5% |

两批 50x8 的 K=4 precision 分别为 93.3%、91.6%，召回为 49.8%、44.3%。
按任务 bootstrap 的 K=4 precision 区间为 88.5%--96.3%，召回区间为 37.7%--59.5%。
这些是探索后的回放与不确定性描述，不是未见任务上的保证。
后层 1/2、全层 1/2、K=4 和主规则在两批 CALVIN 的 107 次失败上都没有报警，也没有成功误报，不能声称跨基准迁移。

**高 precision 经常来自时长。** 首次报警时，与同批次、同任务、同初态、同 query、
仍运行且尚未报警的轨迹匹配，后层 1/2 的 940 个真报警对应随机选择匹配存活者时约 843.2 个的期望。
相对于这个诊断对照只有约 **1.115 倍**，全层 1/2 为 420 / 401.95，约 **1.045 倍**。
K=4 则为 726 / 639.54，约 **1.135 倍**，同样需要谨慎区分总体 precision 与路由增量。
这不是说完全没有路由信息，而是大部分总体 precision 不能归因于路由本身。
对照使用事后标签，只用于诊断，绝不参与报警。

额外信息主要来自 long：550 个真报警，对应 task/init/query 匹配期望约 460.9。
在 spatial 上则为 197 对 196.8，几乎没有增量。
`matched_alarm_specificity.csv` 同时给出仅匹配任务和进一步匹配初态的结果。

固定 query、同任务同初态比较的连续分数也支持这个限制。
第二批 50x8b 中，long 的 q7 AUC 为 0.513，q11 为 0.566，q31 才升到 0.776。
goal/object/spatial 在 q7 的 AUC 分别为 0.414/0.480/0.523。
晚期若只有一两个成功失败配对，AUC 即使为 1 也不可靠，相关样本量与区间已一起输出。
这些窗口是多次描述性比较，未将某个最显著窗口当作独立确认的发现。

## 是否早于物理异常

使用原有物理失败注释中的时间戳做额外对齐；这些时间戳从未进入检测器。
1,403 条失败中，只有 528 条有本次可明确连接的事件代理：463 条首次观察到抓取后释放，65 条目标谓词回退。
其余 875 条不凭最终失败标签强行指定“物理错误开始时刻”。

| 事件代理 | 有时间戳的失败 | 后层 1/2 检出 | 严格早于事件 | 检出者的报警相对事件 |
|---|---:|---:|---:|---|
| 首次观察到抓取后释放 | 463 | 292 | **3** | 中位数晚 8 query |
| 首次目标谓词回退 | 65 | 48 | **27** | 中位数早 5.5 query |

K=4 在这些释放案例中检出 204 条，只有 **1 条**严格早于首次释放，报警中位数晚 10 query；
在 65 条谓词回退中检出 27 条，其中 15 条严格早于回退，检出者中位数提前 5 query。

因此提前于 timeout，并不意味着提前于物理异常。
“首次释放”可能是暂时释放，也不一定是不可恢复的掉落；时间戳只有约一个 action chunk 的观测分辨率。
目标谓词回退也不等于整项任务从此必定失败。本次只能说明与这些事件的先后关系，不能证明因果或不可逆性。

## 另外两种模式的负结果

四次转移的“净位移 / 路径总长”小于 0.25，连续确认两次：检出 751 次失败，却误报 20,688 次成功，
precision 只有 3.50%，低于全体失败率 4.06%。正常路由波动本身也有很小的净位移比例，
不能直接用这个几何量识别机器人陷入错误循环。

动作 token 之间的平方根概率离散程度下降一半：零失败检出、210 次成功误报。
路由收敛或 token 差异减小不能未经验证就解释为错误。
初轮 20 个规则及后续 3 个确认次数变体的完整结果都保留在 `operating_points.csv`，没有删去表现不佳的规则。

- `results/fixed_query_metrics.csv`、`landmark_intervals.csv`：固定时刻、任务与初态匹配后的区分能力。
- `results/rule_deadlines.csv`：截至每个绝对 query 的累计召回和误报。
- `results/overview.png`：固定规则工作点、报警时机，以及后层 1/2 规则的一条失败和一条成功误报。例子按报警时间中位数选择，行号可回查。
- `results/manifest.json`、`extraction_audit.json`、`raw_replay_verification.json`：文件校验和、原始输入核验、流式与批量计算一致性。

```bash
python VLA_MUI_HUB/moe-history-only/analyze.py --workers 4
python VLA_MUI_HUB/moe-history-only/verify.py
python -m pytest VLA_MUI_HUB/moe-history-only -q
```

原始特征按来源缓存。首次执行读取原始 Zarr；后续重用同一份已验证特征。若更换输入数据，
应使用新的输出目录或明确处理旧缓存，不能将缓存检查当作每次对全部 Zarr 的重新校验。

接口示例：

```python
from monitor import HistoryOnlyMonitor, Rule

monitor = HistoryOnlyMonitor()  # 预声明的 1/4 主规则
# 检查预列出的 1/2 敏感性规则时，显式指定：
monitor = HistoryOnlyMonitor(Rule("freeze_back_half", "freeze", threshold=0.5))
# 后续探索的四次确认候选：
monitor = HistoryOnlyMonitor(Rule("freeze_back_half_k4", "freeze", threshold=0.5, confirmations=4))
result = monitor.update(hb_router_probs)  # 单次推理的 [8, 10, 11, 32]
# result['first_alarm_query'] 是真正在线确认的时刻，不回填为更早的开始时刻。
```

`monitor.py` 可直接导入或放到调用方的 Python 路径中；每条 rollout 或 CALVIN 子任务创建一个新实例。
这里未接入实际控制环，没有停止、重采样或修改任何 rollout。

34 项测试通过，覆盖前缀截断、修改未来数据、不混用其他 episode、零基准、阈值平票、流式/批量一致性、
几何循环与单调前进、固定时刻排除时长、任务混杂对照及召回分母。
另从每个来源无标签随机抽一条，91 条共 1,401 次推理，对主规则和 K=4 候选分别验证原始全路由逐步回放与缓存计算的报警一致性。
float32 缓存造成的最大分数误差为约 6.69e-8。

现有证据支持保留“自身路由更新持续减弱”作为可解释的候选风险信号，
同时明确保留误报、漏报和任务迁移失败记录；尚不支持发布一个通用的早期错误判定器。
