# Gate 实验执行说明

## 与前一轮的关系

用户在 P1a 结果后再次要求执行第一步，本轮按独立 gate 探针协议进行。P1a 的冻结配置、数据、阴性门槛判定未改变。P1b 不训练 P1a 的预测器，也不使用 P1a 验证误差挑选 gate 位置。

## 独立运行方式

本轮没有给共享服务添加新接口，没有切换端口或重启 PID 1895。实验脚本在自己的进程中直接调用仓库的 `HiMoEPolicy`，复用 `ScopeBiasCapture` 的实际 gate hook；进程退出后释放自己的 GPU 资源。

独立模型参数仍为 FP32，checkpoint 与原服务相同。关闭 autocast 权重缓存和梯度仅作用于实验进程，目的是限制额外显存。是否保持模型行为通过与原服务和源 trace 的逐状态精确比较验证，不仅凭配置名称判断。

PyTorch 分配器上限为 16384 MiB，CUDA 上下文等不包含在这个上限内，运行前另留显存余量；本轮持续记录实际分配与缓存峰值。

## 审计精度

预检阶段的兼容性单元测试复现了旧全概率审计在 BF16 gate 上可能出现的假不一致。适配代码保留实际干预计算，仅改变审计如何重建权重。

正式采集记录显示，本轮 HB gate 的实际概率运算为 FP32。模型其余部分使用 autocast 不代表每个 gate 都是 BF16，不能把全局设置当成某个算子的实际精度。

后续 P2a 的真实 logits 重放进一步确认：logits / bias 加法为 BF16，而 softmax 概率为 FP32。因此上文的“概率运算为 FP32”不能推导为整个 gate 路径都使用 FP32。证据与审计修订见 [COVERAGE_EXECUTION_NOTES.zh.md](COVERAGE_EXECUTION_NOTES.zh.md)；P1b 的原始数据及判定未改动。

- 采集进程内部：在同一 GPU、同一实际 dtype 下重新计算归一化权重，要求与真正 dispatch 的权重完全相等。
- wire 交叉核对：独立 capture hook 与干预 hook 返回的 ID/权重完全相等。
- CPU 独立复算：四项 FP32 求和的 CPU/CUDA 归约顺序可能不同；明确使用绝对误差上限 `1.2e-7`，并记录实际最大误差。这不放宽前两项完全一致要求，也不改变 gate 运算。
- 重复与撤销：直接比较保存的数组，要求完全相等，不用舍入容差代替。

## 预检成本

- `gate-preflight-gb59_ywi`：成功加载，但因直接对象没有服务层元数据字段而停止；原服务和独立模型推理调用均为 0。
- `gate-preflight-glafkbjc`：4 次独立模型推理和 1 次原服务推理，全部一致；仅零偏置，无非零 gate 探针。

预检是运行条件检查，不是额外的独立父状态或恢复试验。正式实验预算另在冻结配置中列出。CPU 单元测试、原始数组复算不是 VLA 模型前向，不混入模型调用数量。

本轮没有模拟器后缀、物理成功标签或恢复收益，不能把某个位置更敏感解释成它更会恢复。

## 本轮结果与下一步边界

正式 run 为 `runs/p1b-gate-20260914-1nvvkzw2`。569 次正式前向和 5 次预检前向均已核算；13 项单元测试、原始响应独立审计和 597 个产物文件校验已完成。冻结报告及原始数据不再修改。

在单位置 RMS 0.10 下，前四层 / 动作 token / 晚去噪的总动作响应最大，标准化 RMS 为 0.004624。该组直接专家集合变化约 93.2%，但最终动作变化仍较小。不能仅根据大量 top-k 切换认定控制幅度足够。

按总偏置 L2 归一化，前四层 / 状态 token / 晚去噪最高，约为对应动作 token 组的 2.49 倍。动作组干预位置数是状态组的 10 倍；这是事先指定的第二种度量，不是把两个不同预算的实验视为公平等能量对比，也不等于恢复效率。

0.10 / 0.05 的各组平均动作响应比约为 1.00 至 1.22，正负差分跨幅度方向余弦中位数为 0.311。因此，本轮范围不支持简单增加 bias 并期待成比例的动作移动。专家输出相似、共享路径和后续去噪可能影响传递，但缺少专家输出分解，不能把它们当成已验证机制。

若另行开展下一步，可优先冻结晚去噪状态 token 与动作 token 的候选覆盖对照，同时按单位置幅度和总偏置预算分别报告。需要在独立父状态上测量候选是否覆盖有用动作方向；只有实际续跑及预先定义的成功标签才能计算恢复率。本轮没有启动该实验，也没有依据响应排序训练恢复选择器。
