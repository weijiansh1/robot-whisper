# 抓取自检传感器：数据采集计划

日期：2026-09-06
目标读者：执行采集的人
前置结论：`REPORT_ZH.md`

## 0. 为什么要采

路由能在夹爪闭合后 1–2 个 chunk 内读出"这次抓空了"，匹配设计下 AUC 0.89–0.91，
单 query、不看历史、8 个数字。剥离 episode 结局混淆后效应约减半，方向稳固
（48 格中 44 格同向）但**量级不确定**。

卡住结论的**不是方法，是任务覆盖**：

| | |
|---|---:|
| phantom 事件总数 | 232 |
| 出过 phantom 的任务 | **18 / 40** |
| 头 2 个任务占比 | **65%**（KITCHEN_SCENE8 108 个、spatial black_bowl 43 个）|
| 匹配后 155 个 case 中落在这 2 个任务 | **114** |
| 其余有事件任务的率，中位 | **0.562%** |

所以要采的不是"更多事件"，是**更多任务上的事件**。

## 1. 实测约束

全部来自本机与现有语料，不是估计。

| 资源 | 实测 | 瓶颈 |
|---|---|---|
| GPU | 8× H20-3e，143 GB/卡 | 否（见 §1.1）|
| 单进程吞吐 | 2.343 s/次推理，30.8 s/episode（中位）| |
| 16,000 episodes | **149 GPU-小时**（单卡单进程）| |
| CPU | 240 核 | 否 |
| 内存 | 1.9 TB，可用 1.28 TB | 否 |
| **磁盘** | **可用 55 GB** | **是** |
| 现有存储密度 | 22 GB / 32,000 episodes = **0.69 MB/episode** | |

**本机是 H20-3e，不是 H200。** H20 是算力削减版；同样的 rollout 在 H200 上快约 4–7 倍，
下面所有墙钟时间可按该倍数缩短，GPU-小时不变。

**当前 8 张卡被外部进程占满（各 139 GB），开始前必须先释放。**

### 1.1 并发

2.343 s/次推理是 batch-1 的 7B 前向加十步去噪，**单进程远未吃满卡**。
显存允许每卡 8 个进程（7B bf16 约 14 GB），240 核也够 32 个 MuJoCo 环境。
**计算是唯一的限制，且未测。**

规划按**每卡 4 并发 = 32 路**，即 16,000 episodes ≈ **4.7 墙钟小时**，约 **3,400 episodes/小时**。
P0 必须实测这个数，并发上限直接决定 P1 的墙钟。

### 1.2 磁盘是真瓶颈，必须改存储

按现在的存法，55 GB 只够再存 8 万个 episode，且会塞满盘。

**改为闭合触发的窗口存储**：完整 `hb_router_probs [8,10,11,32]` 只在
`[closure-1, closure+4]` 这 6 个 chunk 上写盘；其余 chunk 只写物理状态
（`state (T,8)` + `sim_state (T,79)`，每 chunk 87 个 float，可忽略）。

闭合时刻在线可判（夹爪开度穿越 `CLOSE_APERTURE = 0.05`），不需要事后处理。

估算：从 0.69 MB/episode 降到 **0.15–0.25 MB/episode**，同样的盘可存 **3–4 倍**。
这一条不做，P1 直接撞盘。

**注意**：只存窗口意味着**放弃跨 query 的时序分析**。这是刻意的——本轮已证明
跨 query 那条路失败，而传感器只需要单 query。若日后要重做时序分析，需重采。

### 1.3 不能早截断

我原以为可以在闭合后几步就停。**不行**：phantom 的闭合发生在 chunk **26**（中位），
episode 全长中位 **52**。闭合很晚，因为多数 phantom 是反复尝试后的那一次。

可用的是**标签一旦判定就早停**：在线监控末端位移，一旦
`eef_max_displacement_after >= 0.10 m` 且目标物体未动，phantom 标签已经确定，
可立即结束该 episode。节省约 **20–30%**，不是数量级。

## 2. 目标（定量，先写死）

$$\boxed{\ge 20 \text{ 个 phantom 事件，分布在} \ge 12 \text{ 个不同任务上}}$$

理由：现在的匹配设计只有 10–13 个任务簇，且 114/155 集中在 2 个任务。
达到 12 个任务各 ≥20 个，任务聚类 bootstrap 才有意义，
`diagnose_object_readability_failed.py` 里那个"0 个通过 BH"才可能翻转。

## 3. 三个阶段

### P0 — 扰动标定（先做，它决定 P1 是 2 小时还是 17 小时）

**问题**：能不能通过扰动物体初始位姿把 phantom 率抬上去？

按自然率 0.562% 算，一个任务凑 20 个事件要 3,600 个 episode，
铺 12 个任务 = **43,000 个**（12.7 墙钟小时，且撞盘）。
若扰动能把率抬到 5%，同样目标只要 **4,800 个**（1.4 小时）。

**这一个数字决定 P1 的规模，差 9 倍，所以必须先测。**

设计：

| 维度 | 取值 |
|---|---|
| 任务 | 6 个：2 个高率（KITCHEN_SCENE8、spatial black_bowl）、2 个薄（率 0.5–1%）、2 个零率 |
| 扰动 | 目标物体初始位姿横向偏移 0 / 1 / 2 / 3 cm，方向随机 |
| 每格 | 100 episodes |
| 合计 | 6 × 4 × 100 = **2,400 episodes ≈ 0.7 墙钟小时** |

**同时必须测的**（P0 是唯一的并发标定机会）：
- 每卡并发 1 / 2 / 4 / 8 时的总吞吐 → 定 P1 的并发数
- 窗口存储的实际 MB/episode → 定 P1 的规模上限
- 早停节省的实际比例

**判读**：
- 扰动能把薄任务的率抬到 ≥3% → 走 P1-A（小规模）
- 抬不到 1% → 走 P1-B（大规模），且必须先解决磁盘
- **零率任务在任何扰动下仍为零** → 承认那 22 个任务不产生这种失败，
  目标从 12 个任务下调到 18 个候选里能达标的数量，**不要为了凑数硬扰**

**一条纪律**：扰动改变了分布，所以 P1 采到的**不是自然发生率**。
传感器验证可以用（测的是读数，不是率），但报告里必须写明，
且**不得用它估计 phantom 在真实部署中的发生频率**。

### P1 — 广度采集

按 P0 测出的率分配。规则：

1. **不再跑头 2 个任务**——已有 151 个事件，再跑只会加深集中度
2. 对每个候选任务，episode 数 = `ceil(20 / 实测率)`，上限 6,000
3. 实测率低于 0.2% 的任务直接放弃，不投预算

两种情形的规模：

| 情形 | 每任务 | 12 任务合计 | 墙钟 | 窗口存储 |
|---|---:|---:|---:|---:|
| 扰动后 5% | 400 | 4,800 | 1.4 h | ~1 GB |
| 扰动后 1% | 2,000 | 24,000 | 7.1 h | ~5 GB |
| 自然率 0.562% | 3,600 | 43,000 | 12.7 h | ~9 GB |

三种情形磁盘都够（前提是 §1.2 的窗口存储已实现）。

### P2 — 盲测队列

现有全部结论都在 `external_8b` 上得出，而它在 v3–v7 与本 bundle 中**被反复查看过**，
不是 pristine holdout。传感器要成立必须有一次真正的盲测。

| | |
|---|---|
| 设计 | 全 40 任务，新 seed 批次，**不加扰动**，自然分布 |
| 规模 | 16,000 episodes（50 init × 8 seed × 40 任务）|
| 墙钟 | **4.7 小时** |
| 存储 | 窗口存储约 3 GB |

**纪律**：P2 在 P1 的传感器冻结并哈希之后才开始跑，跑完先封存首报再开标签。
与 v7 的三段纪律一致。

## 6. 明确不做

- **不采跨 query 时序数据。** 窗口存储放弃了它，因为本轮已证明跨 query 那条路失败
  （语料构成漂移 44.5pp、分段抖动、时钟混淆）。
- **不为凑任务数硬扰零率任务。** 22 个任务从不产生 phantom 可能是任务本身的性质
  （非抓取任务、或抓取裕度大），把它们扰出事件是在造数据。
- **不用扰动后的率估计真实发生频率。** 见 §P0 的纪律条。
- **不在 P2 上调任何东西。** 它只有一次用途。
