## Findings

### 1. Intervention Weights Are Not Recorded

`pin-on`, `pin-off`, and `pin-smoke` record the modified expert IDs, but their probability arrays retain the native gate probabilities evaluated at the current gate input. These probabilities do **not** describe the imposed expert mixture.

The [pin hook](/home/jovyan/work/himoe-vla/himoe-route-capture/himoe_switch_intervene.py:94) replaces both IDs and weights. The [recorder hook](/home/jovyan/work/himoe-vla/himoe-route-capture/himoe_router_recorder.py:209) reads the returned IDs but discards `topk_weight`, recomputes softmax, and gathers probabilities at those IDs. Consequently, normalizing `hb_selected_prob` does not recover the weights executed at pinned sites.

Full comparison of the first four HB layers, state token, all denoising steps:

| Run | Pinned sites | IDs match pin table | Maximum weight error | Sites with any weight error > 0.01 |
|---|---:|---|---:|---:|
| pin-on | 202,080 | All | 0.920155 | 201,630 |
| pin-off | 207,040 | All | 0.736542 | 207,030 |
| pin-smoke | 760 | All | 0.624674 | 760 |

The comparison uses nominal pin-table weights before runtime dtype casting. These differences are far larger than rounding error. The original table exists outside the hub at [pin_libero_spatial_pick_up_the_black_bowl_on_th.json](/home/jovyan/work/himoe-vla/pin_libero_spatial_pick_up_the_black_bowl_on_th.json), SHA-256 `f92ec1e99d517eafb1a497f2e9d7e35d5e0c353a4bcee55bbbd0ca60d40997a2`. The run's own capture summary names the regime and layers but does not archive the weight table.

Use these runs as explicitly identified interventions. To analyze their actual mixture, recover the table and regime, or record returned combine weights in a future schema. `hb_entropy` in these runs is also the native gate-distribution entropy, not the entropy of the imposed mixture.

### 2. CALVIN Chain IDs Are Invalid in Both Versions

Both `routes-v1` and `routes-v2-20260903` have all-zero `episode_id`. The [server](/home/jovyan/work/himoe-vla/himoe-route-capture/serve_calvin_with_recorder.py:119) explicitly passes `episode_id=0` on every request. The newer version name does not indicate that this was fixed.

| Run | Completed chains | Official selected universe | Route rows | Local plan |
|---|---:|---:|---:|---|
| cache / routes-v1 | 80 | 1,000 | 3,621 | Truncated probe |
| cache_new / routes-v2-20260903 | 200 | 1,000 | 9,065 | Explicitly requested 200 new chains |

The new run completed its local 200-chain plan; it is not a complete 1,000-chain benchmark evaluation. Its metadata still says `status: prepared` and its client summary correctly says `coverage_complete: false`. The [launch command](/home/jovyan/work/himoe-vla/parallel-route-capture/cmds/calvin-client.sh:10) specifies `--max-new-sequences 200`.

Chain boundaries are recoverable from `client/sequences.jsonl`: repeat each `sequence_index` by its `inference_calls`, or take prefix sums for slices. This audit independently expanded every attempted subtask by `ceil(environment_steps / 10)` and compared its annotation against `server/prompts.json`: **zero count or prompt mismatches in both runs**. Both `state.npy` files and prompt lists have exactly the corresponding number of route rows. Do not group CALVIN by its stored Zarr `episode_id`.

### 3. Old Client NPZ Routing Is Placeholder Data

All **4,098 old LIBERO NPZ files** contain all-zero `expert_ids` and `expert_weights` with shape `(T, 1)`. They are unavailable-data placeholders, not measured routes. Old files also contain an object-valued `layer_indices` field. Its serialized bytes were CRC checked without unpickling.

All **32,000 new LIBERO NPZ files** instead omit routing fields and contain the expected state, action, and simulation-state arrays. This is consistent with the [updated writer](/home/jovyan/work/himoe-vla/himoe-route-capture/rollout_with_routes.py:276). In both generations, obtain actual routes from `server/routes.zarr`.

### 4. Documentation and Naming Do Not Describe Current Inventory

The [README inventory](/home/jovyan/work/himoe-vla/VLA_MUI_HUB/README.md:6) describes the old 76-GB, five-task corpus; it does not describe the new 40-task campaigns. Current `du -sh` reports approximately `2.9G` for `cache` and `22G` for `cache_new`.

The manifest remains a task catalog rather than a current run inventory. Its layout names only `cache`, and its CALVIN task skeleton uses `calvin_d_d`, while actual chain captures are under `calvin_d/task_D_D`.

The writer uses `episode_%02d.npz`, while [corpus_layout.episode_filename](/home/jovyan/work/himoe-vla/himoe-route-capture/corpus_layout.py:242) returns `%04d`. For example, episode 0 is `episode_00.npz`, not `episode_0000.npz`. Use numeric `episode_index` and the actual writer convention; lexical filename sorting is not chronological.

### 5. The Old Baseline Contains a Duplicate Control Run

The ramekin task's `pin-base` and `right-16x32` have identical route-value hashes, and all 512 corresponding NPZ files are byte-identical. Preserve their provenance, but do not count them as independent observations when pooling data.

## How Capture Works

1. The new campaigns invoke `run_corpus_capture.py` through [flat50x8v2.sh](/home/jovyan/work/himoe-vla/parallel-route-capture/flat50x8v2.sh:26) and [b_campaign.sh](/home/jovyan/work/himoe-vla/parallel-route-capture/b_campaign.sh:68). `hubshim/cache` is a symlink to `VLA_MUI_HUB/cache_new`, so the normal corpus driver writes directly into the new cache.
2. The [LIBERO client](/home/jovyan/work/himoe-vla/himoe-route-capture/rollout_with_routes.py:111) sends the observation, prompt, explicit flow noise, and episode ID. It saves pre-execution state and simulation state alongside the predicted action chunk, then executes up to 10 actions.
3. The [server](/home/jovyan/work/himoe-vla/himoe-route-capture/serve_with_recorder.py:655) calls `begin_control_step`, executes policy inference, calls `end_control_step`, and appends the record. One Zarr row means one inference/replanning query, not one environment action.
4. [Gate discovery and attachment](/home/jovyan/work/himoe-vla/himoe-route-capture/himoe_router_recorder.py:181) register PyTorch forward hooks on `gemma_expert.layers.<layer>.mlp.gate`. There are 12 gates in the 18-layer action expert; layers 6-11 are dense and have no router.
5. Each hook takes actual returned expert IDs, recomputes `softmax(F.linear(gate_input, gate.weight))` in the active inference precision context, gathers selected raw probabilities, and computes entropy. Tensors accumulate on device across all 10 denoising iterations, then are transferred and stored as uint8 IDs and float16 probabilities.
6. [AS collapse](/home/jovyan/work/himoe-vla/himoe-route-capture/himoe_router_recorder.py:293) checks that AS routing is invariant across denoising/token axes before storing one result per layer. AS gates read the 24-dimensional action mask, not 1024-dimensional hidden activations.
7. [ZarrRouteWriter](/home/jovyan/work/himoe-vla/himoe-route-capture/himoe_route_store.py:197) buffers records and flushes arrays in chunks. Stores use Zarr v3 with Zstd compression.

| Family / Field | Layer IDs | Stored shape | Meaning |
|---|---|---|---|
| HB expert IDs | 2,3,4,5,12,13,14,15 | `[N,8,10,11,4]` | Actual selected expert IDs |
| HB selected probability | Same | `[N,8,10,11,4]` | Raw softmax probability at selected IDs |
| HB full probability | Same | `[N,8,10,11,32]` | Complete gate probability distribution |
| HB entropy | Same | `[N,8,10,11]` | Natural-log entropy |
| AS IDs / probabilities | 0,1,16,17 | `[N,4]` / `[N,4,3]` | Verified collapsed AS routing |
| Episode / control index | N/A | `[N]` | Episode identity / global inference index |

The 11-token axis is state token 0 followed by action tokens 1-10. On ordinary runs, HB combine weights can be reconstructed as `raw / raw.sum(-1, keepdims=True)`, subject to stored precision. Top-k is unsorted; slot 0 is not necessarily top-1. Stored rounded probabilities can tie at the selection boundary, so validation must allow multiple tied top-4 sets and retain the returned expert IDs as the record of the actual selection.

For each of 88 ordinary runs, the capture summary records 480 successful hook checks: first 4 inference calls x 10 denoising iterations x 12 gates. All failure lists are empty. The three active pin runs intentionally disable this check because they override natural top-k. These are stored capture-time checks, not a new model replay performed by this audit.

## Limits and Recommended Use

Use the two new LIBERO campaigns for routing, state/action, and outcome analysis. The five old `right-16x32` runs also satisfy their selected-task routing plans. Keep active pin interventions separate, and use a sidecar-derived chain mapping for CALVIN.

This hub records routing decisions at replanning queries. It does not provide a complete trace of every expert's output, attention, intermediate denoising action/velocity, or raw RGB frame. Client action chunks include predictions that may not all execute in a successful final query; use `action_steps` to truncate replay. CALVIN saves state and prompts but does not have the LIBERO per-episode action/simulation NPZ payload.

The audit proves present-file readability and the checked internal consistency relations. It does not rerun GPU inference, reconstruct gates from hidden inputs, hash checkpoint files afresh, validate every derived analysis result, or prove byte identity to capture time without historical content hashes.
